# T-CARE — Free deployment (Netlify + Render + existing Supabase)

This deployment keeps the existing Express API intact to minimize deployment changes.

## Services
- Netlify Free: React/Vite frontend (`npm ci && npm run build`, publish `dist`).
- Render Free: Express backend (`backend` root, `npm ci --include=dev && npm run prisma:generate`, start `npm start`).
- Existing Supabase: PostgreSQL and private Storage. Do not create a replacement database.
- Brevo Free: OTP transactional email over HTTPS API (300 emails/day; verify sender first).

## 1. Push this project to GitHub
Commit the project root, including `netlify.toml`, `render.yaml`, `.node-version`, and `public/_redirects`. Never commit `.env` files or secrets.

## 2. Deploy backend on Render
Create a Web Service from the repository. Set Root Directory to `backend`; Render can use `render.yaml` if Blueprint deployment is selected. Choose the Free instance. The build/start/health-check settings are in `render.yaml`.

Set these environment variables in Render (Dashboard → service → Environment):
- `DATABASE_URL`: existing Supabase PostgreSQL connection string. For this long-running Render Node service and the current Prisma CLI configuration, use the Supabase Shared Pooler **Session mode on port 5432** (copy the exact URI from Dashboard → Connect), or a direct connection if the Render network can reach the project’s IPv6 database endpoint. Do **not** use Shared/Transaction Pooler port `6543` with the current single-URL Prisma configuration. Transaction pooling has different prepared-statement/CLI requirements and is intended for short-lived/serverless workloads.
- `SUPABASE_URL`: existing project URL.
- `SUPABASE_SECRET_KEY`: server-only Supabase secret key.
- `SUPABASE_STORAGE_BUCKET`: exact existing private bucket name (default in template: `tcare-media`).
- `FRONTEND_ORIGIN`: exact Netlify production URL, with no trailing slash. Initially use the future Netlify URL and correct it after step 3.
- `BREVO_API_KEY`: Brevo API key.
- `EMAIL_FROM_EMAIL`: sender address verified in Brevo.
- `PAYMENTS_ENABLED`: keep `false` (the Render Blueprint default). This server-side feature gate blocks payment order creation, client verification, refunds and webhooks even if credentials exist.
- `RAZORPAY_KEY_ID`, `RAZORPAY_KEY_SECRET`, `RAZORPAY_WEBHOOK_SECRET`: optional server-only credentials. Leave these unset until Razorpay test mode, signed webhooks, payment idempotency/concurrency handling and the Customer checkout UI have been deliberately enabled and tested. Never put the secret or webhook secret in Netlify.

`JWT_ACCESS_SECRET` and `JWT_REFRESH_SECRET` are generated by the Render Blueprint. If creating the service manually, set two different random values, each at least 32 characters.

Render Free sleeps after 15 minutes of inactivity and can take about a minute to wake. Its filesystem is ephemeral; T-CARE uses Supabase for durable data/files. Render Free blocks SMTP ports, so production OTP delivery uses Brevo's HTTPS API rather than Gmail SMTP.

## 3. Deploy frontend on Netlify
Import the same GitHub repository in Netlify. The checked-in `public/_redirects` routes `/api/*` to `https://t-care-api.onrender.com`; keep that hostname aligned with the existing Render service. Build settings are in `netlify.toml` (Node.js `22.22.0` is pinned):
- Build command: `npm ci && npm run build`
- Publish directory: `dist`
- **Do not set `VITE_API_BASE_URL` in Netlify production.** Leave it unset/blank so the frontend calls `/api/v1` on its own origin and `public/_redirects` proxies `/api/*` to the existing Render service. This avoids bypassing the same-origin proxy.

For local development, create a root `.env.local` with `VITE_API_BASE_URL=http://localhost:4000` while running the frontend on Vite and the API locally. Do not commit `.env.local`.

Deploy, then copy the exact Netlify production URL.

## 4. Finalize backend CORS
In Render, set `FRONTEND_ORIGIN` to the exact Netlify production URL (no trailing slash), then redeploy the backend.

## 5. Database connection and migration safety
The current Prisma schema uses `DATABASE_URL` for both runtime and Prisma CLI operations. Use Supabase Shared Pooler **Session mode (port 5432)** for the Render persistent service if you need IPv4 compatibility, or use the direct database endpoint when IPv6 connectivity is available. Do not paste a Transaction Pooler URI on port `6543` into this current configuration. Supabase documents that transaction mode has prepared-statement limitations; Prisma setups using it need a separately configured pooled runtime URL and direct/session URL for CLI migration work.

The project currently contains five migrations, including the new additive product-catalogue migration. Before applying any migration, inspect the Supabase migration status and confirm which migrations have already been applied. Never run `prisma migrate reset`. Do not run `migrate deploy` blindly against an existing database. The KYC and cancellation migrations may already have been applied by the project owner; verify first.

## Free-tier guardrails
- Do not add a payment method to Render if you want to prevent accidental usage charges; without one, usage limits suspend service instead of charging.
- Netlify Free has a 300-credit monthly hard limit; projects pause at the limit.
- Brevo Free allows 300 email sends/day and includes Brevo branding.
- Render Free backend cold-starts after inactivity. This is acceptable for a low-traffic preview, not a production uptime guarantee.


## Public contact configuration

Set these optional Netlify environment variables for the public contact page:

- `VITE_WHATSAPP_NUMBER`: T-Care's actual WhatsApp Business number in international digits only (for example, country code plus number; do not include `+`, spaces or punctuation). Leave blank until the verified business number is supplied.
- `VITE_PUBLIC_CONTACT_EMAIL`: verified public contact email.
- `VITE_PUBLIC_PHONE_NUMBER`: verified public phone number.
- `VITE_PUBLIC_LOCATION`: approved public-facing office or service-area text.
- `VITE_INSTAGRAM_URL`, `VITE_YOUTUBE_URL`, `VITE_FACEBOOK_URL`, `VITE_LINKEDIN_URL`: optional public profile URLs. Only valid HTTPS URLs are displayed; unset accounts are omitted from the footer.

These values are embedded in the frontend at build time; trigger a new Netlify build after changing them. Do not add private personal contact details.

## Plant Store catalogue

Phase 5 adds the Admin-managed product catalogue. Apply the additive Prisma migration `20261112000200_add_product_catalogue` before enabling the public store. Products are not pre-seeded: Admin must enter approved catalogue data and stock. Product checkout and payment are not enabled by this phase.


## Phase 6 integration and release checks

- Customer billing is a read-only view of the authenticated `/api/v1/payments/customer` ledger. `PAYMENTS_ENABLED=false` blocks order creation, client verification, Admin refunds and webhooks at the backend, even if Razorpay credentials are accidentally added. Backend Razorpay order/verify/webhook and Admin refund routes exist, but they have not been exercised against a Razorpay test account and checkout/refund actions are not surfaced in the current Customer/Admin UI. Do not enable live payment credentials based on source checks alone.
- Customer payment responses use an explicit safe projection; provider IDs, idempotency keys and webhook event payloads are not included in the Customer ledger response.
- Run `cd backend && npm test` for the automated business-rule, payment-view and integration-contract checks.
- Run a real frontend build (`npm ci && npm run build`) and Prisma checks (`cd backend && npm ci --include=dev && npm run prisma:generate && npm run prisma:validate`) in an environment with dependency access before release.
- Verify the additive product migration against the existing Supabase migration history before applying it. Never reset the production database.
- Complete end-to-end smoke testing on a staging deployment before merging or deploying these checkpoint changes.
